Session 結束前的蒸餾與盤點。依序執行以下七個區塊：

**多 session 平行時要一起蒸餾**：同一件事有別的 session 並行做時，§1 到 §4 要涵蓋兩邊，不是只寫自己這條。對方的內容一律從它寫進專案變更記錄的條目取材，不要憑印象或憑它的訊息摘要轉述，那是它自己校對過的版本。

## 1. 精華蒸餾

回顧整個對話，提取：
- 本次做出的重要**決策**（選擇了什麼、否定了什麼）
- 新學到或確認的**知識點**（工具、方法、規則）
- 對未來工作有影響的**洞察**

格式：條列，每條一句話，不超過 8 條。

## 2. 遺漏事項盤點（只抓真正掉出系統的）

只列**未做、且未進任何追蹤系統**的事：沒進等待清單、沒進任務清單、也沒有已知確認時點的，才算遺漏（真的會掉）。
- 討論了方向卻沒落地、也沒記進任何清單的任務
- 用戶說「之後再做」但沒被任何系統接住的暗示

格式：條列，每條標「⬜ 待執行」或「❓ 待確認」，並一句話點「該收進哪個系統」。

⚠️ **已進等待清單、已有確認時點或回追日、已進任務清單、已被某個指令的觸發規則涵蓋的，一律不算遺漏。本 session 該做完的放 §3，其餘放 §4，不要搬來 §2 充數**。若沒有掉出系統的事，直接說「本次 session 無遺漏事項」，不硬湊。這句只代表沒有東西掉出系統，不代表都做完了。

列遺漏前，先用關鍵字 grep 任務清單和相關的 session 記錄，有命中就放 §3 或 §4，不要當成遺漏。

**退役資源要掃殘留。** 本次有刪除或退役的東西（試算表、檔案、習慣、流程），用它的名稱 grep 整個專案資料夾，看還有哪些文件把它當現行流程。命中就列進本區標 ❓，問用戶要不要一起改。

## 3. 本 session 未完成

這個 session 接下來要做完、實際沒做完的事，獨立成一類。**有沒有進任務清單、佇列或派工檔都一樣列在這裡**，因為寫進追蹤系統只代表有人接，不代表做完。

算這類的：
- 本 session 接下的任務、用戶當輪要求的事
- 指令規定本輪要做的步驟
- 改了但沒驗收的東西
- 等用戶回覆才能收的決定

格式：條列，每條寫「什麼事｜為什麼沒做完｜下一步誰做」。

全部做完才寫「本 session 該做的都做完了」。**回報開頭、§1 之上先用一行寫這類有幾件，算在 45 行上限內**，例如「本 session 還有 3 件沒做完」。這類有內容時，不准用「無遺漏」當開頭結論。

## 4. 已規劃事項（本來就不屬於這個 session、已有歸屬、不會掉）

本 session 該做完的不放這裡，放 §3。

未完成或未確認，但**已經被系統接住**的事，列出來讓用戶安心，並明確標示它不是遺漏：
- 已進等待清單（在等別人回應）
- 已有明確確認時點或回追日
- 已進任務清單或排程
- 已被某個指令的警告區或觸發規則涵蓋（呼叫時自動觸發）

格式：條列，每條一句話：什麼事 ＋ 現在歸在哪 ＋ 何時會動。

若沒有這類事項，一句「無已規劃待辦」帶過。

## 5. Memory 建議

**原則：專案導向的細節不進 memory，只進專案文件。**

Memory 只記錄以下類型：
- 用戶的偏好或習慣（user）
- 跨專案適用的 feedback（feedback）
- 用戶透露的背景資訊（user）
- 外部資源的索引位置（reference）

若是專案進度、決策、待辦，一律寫進該專案的變更記錄文件，不進 memory。
若本次建立了新的專案文件：小專案的新文件不提 memory 索引，靠 grep 就找得到；只有跨專案的大專案才提，且 memory 只記「專案名 + 文件路徑」作為索引，不複製內容。

格式：條列說明「建議存入哪類 memory」及「一句話摘要」。

若判斷無新內容值得存，說「本次無新 memory 建議」。

## 6. 專案文檔檢查

若本次 session 有修改程式碼或執行技術操作，檢查以下文件是否已同步更新：
- 變更記錄文件（有沒有記錄本次的操作與結果）
- 架構說明文件（架構或邏輯有沒有改動需要反映）
- **相關流程圖是否最新**：本次動到的專案，連同上層專案，找出所有圖檔原始碼、渲染出的圖片，以及文件裡內嵌的 mermaid 區塊，逐一核對有沒有還寫著舊狀態（「規劃中」「待做」、舊排程、舊機器、舊檔名）。過時就改原始碼、重新渲染並目視確認，圖後的編號說明一起改
- **換掉機制時掃殘留**：本次若換掉某個機制（換 API、換資料源、換工具），用舊名詞（舊端點、舊函式名、舊服務名）grep 整個專案資料夾，把還寫著舊做法的文件一併更新。工作日誌與架構文件都改了，仍可能漏掉某份設計文件
- **修掉一個 bug 時掃同病因**：本次若修了某個根因（權限、路徑、憑證位置、API 限制），用那個根因的特徵 grep 其他同環境的程式，確認沒有第二個中招，有就列進 §2。同一支程式裡做同類判斷的其他分支也要掃：修完要 grep 同一個判斷在檔案裡的每個出現處，只修一處等於留下一模一樣的 bug
- **推翻舊結論時，連產生那個錯誤結論的規則一起改**：本次若更正了某個先前的判斷，除了改案件檔與工作日誌，還要回頭找「當初害你判錯的那條規則寫在哪」，一併改掉。只改案件檔等於源頭還在，下次照樣判錯

格式：
- ✅ 已更新 / ⬜ 未更新 / 無：本次無程式碼改動（不需更新）

若有未更新的文件，直接點名並說明缺少哪些內容，不要只說「建議更新」。

## 7. QA 證據盤點

若本次有寫或改程式（含自用、不上 GitHub 的也算），逐支列出有沒有 QA 證據：

- ✅ 已 QA：有跑過實際指令，並留有輸出
- ⚠️ 未 QA：寫完沒測，直接點名，提醒現在補跑實際測試，並列進 §3

本次沒寫程式則說「本次無程式碼，跳過」。不要放過任何「寫完直接說好了、沒實際跑」的情況。
